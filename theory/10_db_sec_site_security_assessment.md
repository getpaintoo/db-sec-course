# Отчет по анализу защищенности DB_SEC_SITE

## 1. Общая информация

**Объект анализа:** учебное приложение `DB_SEC_SITE` для курса «Безопасность БД».

**Репозиторий:** <https://github.com/Wheatgrh/DB_SEC_SITE>

## 2. Методика

Анализ проводился по следующим направлениям:

- маршруты SvelteKit и серверные обработчики;
- работа с PostgreSQL через `pg`;
- SQL-инициализация схемы, ролей, RLS и функций;
- Docker Compose, `pg_hba.conf`, `postgresql.conf`;
- базовая проверка зависимостей через `npm audit --omit=dev`.

Основной фокус: SQL-инъекции, ошибки разграничения доступа, привилегии БД, хранение учетных данных, настройки контейнеров и PostgreSQL.

## 3. Краткое резюме

Приложение содержит намеренные учебные уязвимости, которые в совокупности дают критический риск при любом размещении за пределами изолированной лабораторной среды.

Наиболее опасная цепочка:

1. пользователь входит под обычной учетной записью;
2. через SQL-инъекцию в поиске или отчетах выполняет произвольную выборку;
3. из-за `BYPASSRLS` и широких прав `app_user` получает доступ к данным всех пользователей;
4. через уязвимый API профиля повышает свою роль до `admin`;
5. при доступности PostgreSQL по сети может подключиться к БД без пароля из-за `trust` в `pg_hba.conf`.

### DBSEC-01. SQL-инъекция в поиске клиентов

**Где найдено:**

- `src/routes/catalog/+page.server.ts:9-15`
- `src/lib/server/db.ts:102-118`

**Описание.**

Параметр `q` из URL передается в `unsafeSearchCustomers()`. Далее значение напрямую вставляется в SQL-строку:

```ts
const sql = `SELECT id, full_name, email, tier, owner_user_id
	FROM training.customers
	WHERE email ILIKE '%${normalized}%'
	ORDER BY id`;
```

Это позволяет изменить структуру SQL-запроса. Даже простой ввод вида `' OR true --` превращает фильтр в условие, возвращающее все строки.

**Риск.**

Обычный пользователь может получить чужие записи клиентов. С учетом широких прав `app_user` и `BYPASSRLS` уязвимость может использоваться не только для чтения, но и как входная точка для более опасных действий с БД.

**Как исправить.**

Использовать параметризованный запрос:

```ts
const result = await pool.query(
	`
		SELECT id, full_name, email, tier, owner_user_id
		FROM training.customers
		WHERE email ILIKE '%' || $1 || '%'
		ORDER BY id
	`,
	[normalized]
);
```

Дополнительно нужно ограничить права `app_user`, убрать `BYPASSRLS` и добавить проверку, что пользователь видит только свои записи либо записи, разрешенные его ролью.

### DBSEC-02. SQL-инъекция в `SECURITY DEFINER`-отчете

**Где найдено:**

- `src/routes/reports/+page.server.ts:21-33`
- `src/lib/server/db.ts:224-230`
- `db/init/01-schema.sql:66-88`

**Описание.**

Форма отчетов принимает произвольный `WHERE fragment`. На уровне приложения значение передается параметром в функцию `training.run_custom_report($1)`, но внутри PostgreSQL функция собирает динамический SQL через `format(... WHERE %s, raw_where_clause)`.

Функция объявлена как `SECURITY DEFINER`, поэтому выполняется с правами владельца функции, а не вызывающего пользователя.

Пример безопасного для лабораторной проверки payload:

```sql
true UNION SELECT username, 0::numeric, password, role
FROM training.app_users --
```

Такой ввод может вернуть учетные записи и пароли, потому что результат приводится к ожидаемым четырем колонкам отчета.

**Риск.**

Критическое раскрытие данных. Пользователь, имеющий доступ к странице отчетов, может читать данные вне своей зоны доступа, обходить RLS и извлекать данные из таблиц, которые не должны попадать в отчет.

**Как исправить.**

- не принимать SQL-фрагменты от пользователя;
- заменить произвольный `WHERE` на белый список фильтров: владелец, статус, диапазон сумм, даты;
- убрать `SECURITY DEFINER`, если повышенные права не нужны;
- если `SECURITY DEFINER` все же нужен, явно задать безопасный `search_path` и минимальные права;
- формировать SQL только из заранее известных колонок и операторов, значения передавать параметрами.

### DBSEC-03. Неэффективная RLS и чрезмерные права `app_user`

**Где найдено:**

- `db/init/01-schema.sql:10`
- `db/init/01-schema.sql:57-64`
- `db/init/01-schema.sql:90-96`

**Описание.**

Для `training.customers` включена RLS и создана политика по `current_setting('app.current_user_id')`. Но роль приложения получает `BYPASSRLS`, поэтому RLS для нее не применяется:

```sql
ALTER ROLE app_user BYPASSRLS;
```

Также `app_user` получает полные DML-права на все таблицы схемы:

```sql
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA training TO app_user;
```

При этом приложение не устанавливает `app.current_user_id` перед запросами, поэтому даже после удаления `BYPASSRLS` текущая политика не заработает корректно без доработки.

**Риск.**

Любая SQL-инъекция или ошибка бизнес-логики автоматически получает доступ ко всем таблицам приложения. RLS существует в коде, но фактически не защищает данные.

**Как исправить.**

- удалить `ALTER ROLE app_user BYPASSRLS`;
- заменить широкие grants на минимальные права для конкретных таблиц и операций;
- включить RLS для `customers`, `invoices`, при необходимости `audit_events`;
- перед запросами в рамках транзакции устанавливать контекст:

```sql
SET LOCAL app.current_user_id = '<uuid текущего пользователя>';
```

- добавить политики для чтения и изменения:

```sql
CREATE POLICY invoice_owner_read
	ON training.invoices
	FOR SELECT
	USING (
		owner_user_id = current_setting('app.current_user_id')::uuid
	);
```

### DBSEC-04. Доверительная PostgreSQL-аутентификация и открытый порт БД

**Где найдено:**

- `db/pg_hba.conf:1-4`
- `db/postgresql.conf:1`
- `docker-compose.yml:5-10`
- `docker-compose.yml:22-28`

**Описание.**

PostgreSQL слушает все интерфейсы:

```conf
listen_addresses = '*'
```

Порт БД проброшен на хост:

```yaml
ports:
  - "5432:5432"
```

При этом `pg_hba.conf` разрешает подключение без пароля:

```conf
host all all 0.0.0.0/0 trust
host all all ::/0 trust
```

**Риск.**

Любой пользователь, имеющий сетевой доступ к порту 5432, может подключиться к PostgreSQL без пароля, в том числе от имени `postgres`, если окружение не изолировано.

**Как исправить.**

- заменить `trust` на `scram-sha-256`;
- не публиковать порт БД наружу, если доступ нужен только приложению;
- ограничить `listen_addresses` внутренней Docker-сетью или `localhost`;
- вынести пароли в секреты или переменные окружения, не хранить production-пароли в compose-файле;
- создать отдельные роли БД с минимальными правами.

### DBSEC-05. IDOR и mass assignment в API профиля

**Где найдено:**

- `src/routes/api/users/[id]/profile/+server.ts:4-28`
- `src/lib/server/db.ts:175-207`

**Описание.**

API профиля проверяет только факт аутентификации. `params.id` берется из URL, а `roleName` доверяется из тела запроса:

```ts
const userId = params.id.trim();
const roleName = String(form.get('roleName') ?? '').trim();
```

Если `roleName` передан, `updateUserProfile()` обновляет роль пользователя:

```sql
UPDATE training.app_users
SET full_name = $1,
    email = $2,
    role = $3
WHERE id = $4
```

**Риск.**

Любой аутентифицированный пользователь может изменить профиль другого пользователя, если знает его UUID. Также можно повысить себе или другому пользователю роль до `admin`, передав скрытое поле `roleName=admin`.

**Как исправить.**

- для обычного пользователя разрешать обновление только `locals.user.id`;
- изменение роли вынести в отдельный admin-only endpoint;
- проверять роль на сервере, а не полагаться на отсутствие поля в UI;
- валидировать `roleName` по белому списку;
- записывать изменение роли в аудит.

### DBSEC-06. IDOR при просмотре счетов

**Где найдено:**

- `src/routes/invoices/[id]/+page.server.ts:4-14`
- `src/lib/server/db.ts:122-140`
- `db/init/02-seed.sql:16-21`

**Описание.**

Маршрут `/invoices/[id]` проверяет только наличие сессии. Запрос `getInvoiceById()` фильтрует счет только по UUID:

```sql
WHERE i.id = $1
```

Проверки владельца, роли пользователя или RLS для таблицы `training.invoices` нет.

**Риск.**

Любой вошедший пользователь может открыть чужой счет по известному UUID и увидеть сумму, статус, `card_hint`, внутренние заметки и владельца.

**Как исправить.**

Добавить проверку владельца и роли:

```sql
WHERE i.id = $1
  AND (
  	i.owner_user_id = $2
  	OR $3 IN ('manager', 'admin')
  )
```

Лучше дополнительно закрепить это на уровне БД через RLS для `training.invoices`.

### DBSEC-07. Недостаточные проверки ролей для аудита и отчетов

**Где найдено:**

- `src/routes/audit/+page.server.ts:4-10`
- `src/lib/server/db.ts:211-219`
- `src/routes/reports/+page.server.ts:16-25`

**Описание.**

Журнал аудита и пользовательские отчеты доступны любому аутентифицированному пользователю. Разделы содержат служебные события, SQL-детали и финансовые данные.

**Риск.**

Пользователь с минимальной ролью получает доступ к административной информации и данным, которые должны быть доступны только менеджеру или администратору.

**Как исправить.**

- добавить серверную проверку `locals.user.role`;
- аудит выдавать только `admin`;
- отчеты ограничить ролью `manager`/`admin` и фильтрами по владельцу;
- добавить тесты на `403 Forbidden` для роли `student`.

### DBSEC-08. Небезопасное хранение паролей и слабая модель сессий

**Где найдено:**

- `db/init/01-schema.sql:14-21`
- `db/init/02-seed.sql:3-7`
- `src/lib/server/db.ts:48-75`
- `db/init/01-schema.sql:23-27`
- `src/routes/login/+page.server.ts:25-30`

**Описание.**

Пароли хранятся в открытом виде в колонке `password` и сравниваются напрямую в SQL:

```sql
WHERE username = $1
  AND password = $2
```

Сессии имеют только `created_at`, но не имеют серверного срока действия. Cookie выставляется с `secure: false`.

**Риск.**

При утечке БД или SQL-инъекции раскрываются реальные пароли. Украденный `session_id` остается действующим до ручного удаления записи. Cookie без `secure` может передаваться по HTTP.

**Как исправить.**

- заменить `password` на `password_hash`;
- использовать Argon2id или bcrypt с индивидуальной солью;
- добавить `expires_at` в таблицу `sessions` и проверять срок действия в `getUserBySession()`;
- выставлять `secure: true` в production;
- добавить rate limit и задержки на неуспешный вход.

### DBSEC-09. Раскрытие технических ошибок и избыточное логирование SQL

**Где найдено:**

- `src/routes/reports/+page.server.ts:30-34`
- `db/postgresql.conf:4-7`

**Описание.**

Страница отчетов возвращает пользователю текст исключения БД:

```ts
error: err instanceof Error ? err.message : 'Unknown SQL error'
```

PostgreSQL настроен на `log_statement = 'all'`, что полезно для лаборатории, но рискованно для реальной среды.

**Риск.**

Ошибки помогают уточнять структуру БД при SQL-инъекции. Полное логирование SQL может раскрывать служебные данные, фильтры отчетов и пользовательские вводы.

**Как исправить.**

- пользователю возвращать общее сообщение об ошибке;
- подробности писать в защищенный серверный лог;
- для production использовать более сдержанный уровень логирования;
- исключить чувствительные данные из логов.

### DBSEC-10. Недостаточное hardening-контейнера и устаревшая зависимость

**Где найдено:**

- `Dockerfile:1-13`
- `package-lock.json`

**Описание.**

Контейнер приложения запускается без отдельного непривилегированного пользователя. В Dockerfile используется `npm install`, хотя для воспроизводимых сборок лучше использовать `npm ci`.

`npm audit --omit=dev` показал 3 low-уязвимости, связанные с пакетом `cookie` через `@sveltejs/kit`.

**Риск.**

Риск ниже, чем у прикладных SQL- и authz-ошибок, но при эксплуатации приложения root-процесс в контейнере увеличивает последствия побега из процесса Node.js.

**Как исправить.**

- использовать `npm ci`;
- запускать Node.js от непривилегированного пользователя;
- обновить SvelteKit/зависимости после проверки совместимости;
- добавить регулярный dependency audit в CI.

## 5. Рекомендуемый план исправлений

### Этап 1. Срочные меры

1. Закрыть внешний доступ к PostgreSQL и убрать `trust` из `pg_hba.conf`.
2. Убрать `BYPASSRLS` у `app_user`.
3. Исправить SQL-инъекцию в поиске клиентов.
4. Отключить произвольные SQL-фрагменты в отчетах.
5. Запретить изменение роли через API профиля.

### Этап 2. Разграничение доступа

1. Добавить серверные проверки ролей для аудита, отчетов, счетов и профилей.
2. Включить RLS для таблиц `customers` и `invoices`.
3. Передавать текущего пользователя в PostgreSQL через `SET LOCAL app.current_user_id`.
4. Разделить права БД: чтение каталога, работа с сессиями, административные операции.

### Этап 3. Учетные данные и эксплуатационная безопасность

1. Перейти на хеши паролей.
2. Добавить срок действия серверных сессий.
3. Включить `secure` cookie в production.
4. Убрать технические ошибки из UI.
5. Обновить зависимости и усилить Dockerfile.

## 6. Проверочные сценарии после исправлений

После внесения исправлений нужно проверить:

- поиск клиентов с вводом `' OR true --` не возвращает чужие записи и не ломает SQL;
- отчет не принимает произвольный SQL, а работает только с разрешенными фильтрами;
- пользователь `alice` не может открыть счет `bob` или `carol`;
- пользователь `alice` не может изменить профиль другого пользователя;
- `roleName=admin` в POST-запросе к профилю игнорируется или возвращает `403`;
- `/audit` недоступен для роли `student`;
- прямое подключение к PostgreSQL без пароля невозможно;
- `app_user` не имеет `BYPASSRLS` и не может читать таблицы вне разрешенных политик;
- `npm audit --omit=dev` не показывает уязвимостей уровня moderate и выше.

## 7. Вывод

Учебное приложение хорошо демонстрирует типичные ошибки безопасности БД и веб-приложений: SQL-инъекции, неправильную модель привилегий, неработающую RLS, IDOR, хранение паролей в открытом виде и слабые настройки PostgreSQL.

Ключевой вывод для курсовой работы: защита должна строиться слоями. Параметризованные запросы, серверная авторизация, минимальные права роли БД и RLS должны работать одновременно. Если один слой дает сбой, остальные должны ограничить ущерб.
